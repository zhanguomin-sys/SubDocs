# 版本规划

## 版本原则

- 每个版本只完成本节列出的范围，不把后续功能提前塞入当前版本。
- 已完成、草案和未来计划必须分开标注。
- 模型能力以真实测试为准；没有 macOS、Windows 或远端环境证据时，不写成已经验证。

## V0.1：`gpt-image-2` 生图脚本

状态：已完成。

包含：

- 固定调用 `https://api.myautoapi.com/v1/images/generations`。
- 只支持 `gpt-image-2`，固定 `n=1`。
- 默认使用 `1024x1024`、`high`、`png`，允许调用方覆盖图片参数。
- API Key 由脚本从约定位置读取，不接受命令行密钥。
- 同时处理 `b64_json` 和 URL，Base64 优先，URL 只下载一次。
- 保存脱敏请求、原始响应、响应头、实际图片和运行摘要。
- 根据实际文件签名命名图片，并尽可能记录实际尺寸。
- 无密钥自动化测试和 Linux 真实烟雾验证。

不包含：

- 安装到 Codex Home。
- 安装或正式发布 Skill。
- 一键配置、自动升级、其它模型和视频模型。
- macOS、Windows 真实运行验证。

## V0.2：一键安装与完整使用流程

状态：`V0.2-r1` 已验证不适合作为通用发布，因为客户端必须已有 Python。`V0.2-r2` 完成原生实现但发布平台过多。当前 `V0.2-r3` 只发布 Windows x64 和 Apple Silicon Mac；两者真实运行仍需分别验证。

计划包含：

- Apple Silicon Mac 的 Bash 一键脚本和 Windows x64 的 PowerShell 一键脚本。
- 尊重 `CODEX_HOME`，未设置时回退当前用户的 `.codex`。
- 安装正式脚本和 Skill，并支持重复执行和已有文件处理；生图脚本直接读取 Codex `auth.json`，安装器不读取、写入或复制 API Key。
- 使用系统和用户目录的正常默认文件权限，不强制 `0600`，不额外重写 Windows ACL。
- 说明 AI 如何调用 Skill、怎样传入参数、成功后怎样查看图片、失败后怎样保留记录。
- 决定是否以及如何写入用户的 `AGENTS.md`，明确影响范围和保留已有内容的方式。
- 子项目内保留安装、首次使用、失败处理和卸载说明；不修改父项目 `subdocs/docs/`、站点页面或导航。
- 完成卸载和重新安装边界，但不做远端自动升级。
- 在线入口按操作系统和架构下载版本化原生程序，并在运行前校验内置 SHA-256；客户端不安装 Python、Node 或 SDK。
- `V0.2-rN` 仅是同一 `0.2.0` 安装状态的分发修订；它可修复同版本托管文件，但不承担 V0.3 的版本升级或降级。

## V0.3：专门画图分组 Key 与可控更新

状态：已完成并于 `V0.3-r5` 发布，后续能力统一由 `V0.7.0` 公网版本承接。专门 Key、原生安装、基础生图流程、Skill 调用修正和用户主动触发的可控更新已经完成。公网只保留 Windows、Mac 两个安装入口和当前版本构建。Windows 已完成真实生图验证，Apple Silicon Mac 仍待真实机器验证。

包含：

- 安装器首次运行时要求用户粘贴“专门画图分组”的 Key，输入内容正常显示在终端中。
- Key 保存到 `$CODEX_HOME/tools/myautoapi-imagines-tool/api-key`，不写入安装清单、日志或临时磁盘备份。
- 工具默认从工具目录读取专门 Key；旧版 `auth.json` 读取保留为隐藏内部模式，不在 Skill 或安装主路径中展示。
- 组合快速开始入口使用内部比较模式，发现专门 Key 与编程 Key 完全相同时提醒用户；确认提示直接回车表示同意，输入 `N` 退出生图安装。
- 独立运行生图安装器时不读取 `auth.json` 做比较，只显示“专门画图分组”核对提醒。
- 从 V0.2 原生安装升级到 V0.3；安装失败恢复已有文件和 Key 状态。
- 只构建和发布 Windows x64、Apple Silicon Mac 两个平台程序，在线入口按当前系统按需下载一个程序。
- 生图结果不写入 Codex Home；有项目或工作区时写入项目根目录的 `images`，没有项目或工作区时由 Skill 写入桌面的 `images`。
- Skill 只执行一个前台工具命令并等待同一命令完成；不搜索工具、预建目录、扫描记录或另查进程。
- 用户明确对 Codex 说“更新生图工具”后，由 Codex 在当前任务中自行完成检查、下载、安装和验证；不要求用户再次粘贴命令。
- 更新继续使用稳定的一键安装入口，不创建系统后台服务、计划任务、开机检查，也不在正常生图时检查远端版本。
- 增加独立发布修订号，使本地能够区分 `V0.3-r3`、`V0.3-r4` 等同一 `0.3.0` 下的修订；已是最新版时不下载原生程序。
- 发现新修订时只下载当前平台的一个程序，校验 SHA-256 后事务更新；失败时恢复原有工具、Skill 和规则。
- 已有非空“专门画图分组 Key”时原样保留，不读取、不展示、不再次要求输入；只有首次安装或 Key 缺失、为空时才输入 Key。
- V0.3 的普通修正继续使用 `V0.3-rN`，不升级为 `0.4.0`。安全问题、接口失效或安装阻断可以立即发布；普通修改合并验证后再发布，避免频繁产生新的原生程序。

不包含：

- 其它图片模型、视频能力和参数矩阵补全。
- 父项目快速开始脚本的合并迁移；该入口待本子项目稳定后单独接入。
- Windows 代码签名和 macOS 签名、公证暂不纳入当前范围；收到真实拦截反馈后再单独评估。

## V0.4.0：完成 `gpt-image-2` 文生图

状态：已完成并纳入 `V0.7.0` 公网版本。源码实现、真实参数验证、独立审核和 Windows x64 / Apple Silicon Mac 发布构建均已完成。

包含：

- 图片输出固定为 PNG；不把线路没有稳定兑现的 JPEG、WebP 写成已支持。
- 项目存在时直接保存到项目 `images`，没有项目时保存到桌面 `images`；每次只留下最终图片，不创建图片专属子目录和运行记录文件。
- 根据画面主体使用简短准确的文件名，重名自动追加数字，不覆盖旧图。

- 保持固定模型、固定接口、专门画图 Key、单次请求、无自动重试和安全重定向边界。

不包含：

- 参考图、修图、蒙版、其它图片模型和视频模型。
- `n` 多图、压缩率、透明背景或额外格式选择。
- 面向用户的参数测试报告、原始响应和调试目录。

## V0.4.1：参考图、修图与多图结果

状态：已完成源码和真实接口验证，并纳入 `V0.7.0` 公网版本。

- 使用用户提供的一张或多张图片作为参考素材，或作为修改目标。
- `edit` 通过 multipart 图片输入调用固定编辑接口；用户没有说明图片角色时只补问角色。
- `generate --n N` 支持同一画面要求的多张结果。中转站忽略 `n` 时，在同一次工具调用中用单图请求补齐数量。
- 单图返回 `output_file`，多图返回 `output_files`；Skill 按数组顺序逐张调用 `view_image`，所有图片显示后才报告成功。
- 修改结果另存为新图片，不覆盖原图；输入图片和临时上传体不写入用户 `images`。
- 不扩展蒙版编辑、透明背景、批处理系统、其它模型和低频边缘参数。

## V0.5.0：已验证的其它图片模型

状态：已完成源码、真实接口探测和无密钥回归测试，并纳入 `V0.7.0` 公网版本。

包含：

- 支持 `gpt-image-1k-th`，固定 `1024x1024`，已验证 `low`、`high`、参考图和修图；多图固定拆成单张请求。
- 支持 `gpt-image-2-adobe`，默认使用 `1024x1536`、`low`，并开放已验证的 `1536x2304`、`2304x3456` 尺寸；只开放文生图能力。
- 保留 `gpt-image-2` 的全部 V0.4.1 能力，默认参数和参考图、修图入口不变。
- Adobe 的多图由原生工具在同一次命令内拆成多次单张请求；不依赖上游的 `n=3`。
- Skill 在用户询问模型时列出三个已支持模型；用户明确要求比较时才逐个调用，不自动比较画面质量。
- 模型专属默认尺寸和质量写入工具参数校验，未验证的价格表旧别名不加入支持列表。

真实探测结论：`gpt-image-1k-th` 的 `1024x1024`、`low`/`high`、修图均成功；上游对原生 `n=3` 曾分别返回一张和四张，因此工具不再直传多图数量。`gpt-image-2-adobe` 的 `1024x1536`、`1536x2304`、`2304x3456` 在 `low` 下各重复两次均成功，返回对应 PNG；`medium`、`high` 和原生 `n=3` 返回 `503 No available compatible accounts`，修图同样不可用。`gpt-image-2k-adobe`、`gpt-image-4k-adobe` 等旧别名返回 404，不作为模型名。`ad-gpt-image-2-mx` 在 Images 与 Responses 入口分别返回模型不受 Images 路由支持和上游拒绝访问，因此不作为可调用模型。

不包含：

- 不比较不同模型的画面质量，不替用户选择风格或内容。
- 不加入 `gpt-image-1k-adobe`、`gpt-image-2k-adobe`、`gpt-image-4k-adobe` 等当前 Key 不可用的旧别名。
- 不加入 `ad-gpt-image-2-mx`、视频模型、蒙版或后台自动更新。

## V0.6.0：Grok Imagine 图片能力

状态：已完成真实接口探测、源码、Skill、安装规则和测试，并纳入 `V0.7.0` 公网版本。

- 支持模型 `grok-imagine-image`，继续使用统一的 `generate` 和 `edit` 命令。
- 文生图支持 `1k`、`2k`，以及 `1:1`、`16:9`、`9:16`、`4:3`、`3:4`、`3:2`、`2:3` 七种常用比例。
- 质量参数支持 `low`、`medium`、`high`；未指定时使用模型默认质量。
- 原生 `n=3` 一次返回三张有效图片；工具沿用 `output_files` 和逐张展示契约。
- 参考图和修图使用 `/v1/images/edits`，传入原图和完整修改要求。
- Grok 请求使用独立的 `resolution`、`aspect_ratio` 和 `response_format` 转换，不复用 GPT Image 的像素尺寸请求体。
- 返回图片按文件签名保存；本次实测 1K 为 JPEG、2K 为 PNG，用户目录仍只保留最终图片。
- 父项目“生图分组方法”页同步四个已支持模型及 Grok 的可用参数。

## V0.7.0：Nano Banana 图片能力

状态：已完成并发布 `V0.7.0`。真实接口已确认两个模型均能返回有效 PNG，工具可解析、保存并显示；Skill、安装规则和本地契约测试均已完成。

- 支持 `nano-banana-2` 和 `nano-banana-pro`，继续使用统一的 `generate` 与 `edit` 命令。
- 两个模型都通过 `/v1/responses` 发送文本、规格和可选参考图，不复用 Images JSON 或 multipart 请求。
- `nano-banana-2` 开放 `512`、`1k`、`2k`、`4k`；`nano-banana-pro` 开放 `1k`、`2k`、`4k`。
- 两个模型开放 `1:1`、`3:2`、`2:3`、`3:4`、`1:4`、`4:1`、`4:3`、`4:5`、`5:4`、`1:8`、`8:1`、`9:16`、`16:9`、`21:9`、`9:21`。
- 参考图和修图最多接收 14 张 PNG、JPEG 或 WebP；输入图只编码到内存请求，不写入输出目录。
- 多图由一次工具调用内部按单张 Responses 请求补齐；stdout 返回 `output_files`，Skill 逐张显示。
- 解析 `output` 内的结构化图片、Markdown Data URL 和 HTTPS 图片链接；按文件签名保存最终图片。
- 工具只负责参数转换、请求、保存和展示，不替用户选择画面内容、风格或模型效果。

## V0.7.1：多模型并发与结果展示

状态：本地实现和无密钥测试已完成，尚未迁移到父仓库或公网发布。

- 单模型任务仍只运行一次原生工具；同一模型的多张结果仍使用一次 `--n N`，不拆成多个进程。
- 用户明确要求两个或更多不同模型分别生成时，每个模型使用一个独立前台工具调用，并由 Codex 在同一批中并发启动。
- 并发由宿主的多工具调用能力完成，不使用 shell 后台符号、PowerShell `Start-Job`、脱离会话任务或进程轮询。
- Codex 保存模型、调用和 stdout 结果的对应关系，不根据完成顺序或文件名猜测模型。
- 对每个结果文件调用 `view_image` 前写出准确模型 ID；同一模型多张图时同时写出当前张数。
- 一个模型失败时仍展示其它模型的全部成功图片，并单独报告失败模型；所有成功图片显示完成后才报告任务完成。
- 不新增模型，不修改各模型 API、参数转换、图片保存或 Key 读取逻辑。

## V0.8.0：GPT Image 2.5 与默认 2K

状态：源码、最小真实接口验证、独立审查和父仓库发布迁移已完成；尚未提交或发布。

- 新增 `gpt-image-2.5-flare` 和 `gpt-image-2.5-sunburst`，两者均复用现有 Images 生图、multipart 修图、响应解析、多图和保存流程。
- 模型选择顺序固定为：用户明确指定模型时始终服从；未指定模型且明确要求高清、高质量、精细细节、精修、严格保留原图或重要成品时使用 Sunburst；其余未指定模型的任务默认使用 Flare。
- 两个新模型默认使用 `2048x2048`、`high`、`png`；2K 横图和竖图分别使用 `2048x1152` 和 `1152x2048`，不使用 `resolution=2k`。
- 两个新模型支持 `low`、`medium`、`high`、`xhigh`、`max`、`auto`；`xhigh` 和 `max` 不向旧模型扩散。
