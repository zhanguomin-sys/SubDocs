# Codex 桌面 App 升级兼容性讨论

状态：历史源码研究备查。开发按精简后的 [开发文档](开发文档.md)执行，本记录不增加自动同步或兼容系统的实施要求。

日期：2026-10-14。
参与：主代理与用户指定的子代理 `upgrade_review`。
对象：[开发文档](开发文档.md)第 5、10、11 节。
范围：源代码和官方文档核对，尚未在 Windows/macOS 桌面 App 上进行实际升级测试。

## 1. 先定义升级后要保住什么

| 要求 | 当前方案能够支持到什么程度 |
| --- | --- |
| 用户配置与模型文件不随安装包更换而被覆盖 | 文件放在用户配置目录，正常升级预期保留，需实际升级确认 |
| 已导入 GPT 与自定义模型继续存在 | 旧目录能被新后端接受时可以继续加载，不能仅凭文件存在保证 |
| 模型能力声明和实际请求不因字段变化而错误 | 对已知版本组合核对字段兼容并验证实际请求，不能只做 JSON 语法检查 |
| 新版 App 新增 GPT 自动出现在同一列表 | 静态完整目录不会自动合并新版内置目录，目前没有原生配置开关实现 |
| 永久兼容所有未知未来版本 | 一次性导入脚本无法提供这个保证 |

“不用每次升级重新导入”应当是已验证版本组合的验收目标。不能把“用户一定会手动重跑”作为自动更新设计，也不能把新增 GPT 自动同步与现有模型继续有效混为一个要求。

## 2. 双方分别核对的证据

主代理核对正式发布版 `rust-v0.162.1` 与历史版 `rust-v0.134.0` 的目录字段和请求构建；子代理独立核对静态目录、App 模型刷新与任务启动 hook 的调用顺序。双方互相检查关键源码片段。

### 目录替换与刷新

设置本地目录后，正式版立即创建 `StaticModelsManager`，没有与内置 GPT 目录自动合并的步骤。静态管理器的目录读取返回内存中的条目，忽略刷新策略，ETag 刷新是空操作。

证据：[模型管理器创建](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/model-provider/src/provider.rs#L388)、[静态模型管理器](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/models-manager/src/manager.rs#L800)。

### 解析失败没有内置目录回退

文件读取或反序列化失败会返回错误，并从配置构建流程传播。不能假设升级后目录不兼容时，Codex 会自动忽略目录、恢复原 GPT 并继续启动。

证据：[目录加载与错误传播](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/core/src/config/mod.rs#L2160)。

### 已存在的兼容支持

`0.162.1` 仍接受旧 `base_instructions`，并将其提升为新的模型指令结构；多数新增字段有默认值。说明旧目录并非遇到升级就必然失效，也不需要为每次升级设计一次强制重跑。

证据：[旧指令字段转换](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/protocol/src/openai_models.rs#L895)。

### 解析成功不等于行为一致

`0.134.0` 的 `supports_reasoning_summaries` 控制整个推理请求对象，而 `0.162.1` 的 `supports_reasoning_summary_parameter` 只控制摘要字段，新字段默认值为真。旧目录中的关闭声明不能机械地按名字转成新字段，更不能假设旧字段被忽略后行为没有变化。

证据：[旧版推理请求构建](https://github.com/openai/codex/blob/rust-v0.134.0/codex-rs/core/src/client.rs#L698)、[新版推理请求构建](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/core/src/client.rs#L870)。

### 主动更新可以简化修复

`0.162.1` 的 `debug models --bundled` 分支先直接导出二进制内置目录，不用用户配置构造模型管理器。因此主动更新时，可在旧目录已经无法解析的情况下取得新版 GPT 数据，而不先改坏目录指向。App 自带后端是否支持此命令须按实际版本验证。

证据：[内置目录导出分支](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/cli/src/main.rs#L2093)。

## 3. 讨论后排除的方案

不采用任务启动 hook 自动重建目录。配置和目录已经先解析，SessionStart 才执行；静态模型管理器也已经构造。hook 更新文件最多影响之后的完整启动，不能救首次升级启动时的解析失败。再由 hook 强行杀 App 重启，会引入任务中断与重复启动问题。

证据：[可配置 hook 事件](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/config/src/hook_config.rs#L36)、[SessionStart 执行位置](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/core/src/session/session.rs#L1938)。

也不依赖 App 定期刷新来重新合并本地目录，不修改 App 安装包或更新程序，不擅自增加常驻程序、系统定时任务或启动入口包装。

## 4. 最小实现与验收建议

1. 配置及完整模型目录始终放在用户配置目录，使用稳定的绝对路径，保留原默认 GPT 和认证。
2. 依据目标 App 后端生成正确目录；保留已知兼容字段，对自定义模型准确处理不同版本的能力声明。
3. 使用同一份旧版导入结果做升级测试：升级前后不重跑脚本，核对文件与目录指向、App 加载、GPT 与国产条目、能力选项和实际请求字段。
4. 对明确验证过的版本组合记录兼容结果。源码对比不代替实际 App 升级测试，不把 CLI 发布版本直接当作桌面 App 的后端版本。
5. 用户主动重跑时刷新目录；支持内置目录导出的后端直接用于更新和修复。

这套方案保证目标是“已验证的升级不需要用户重新导入，现有模型继续有效”。未来新增 GPT 自动合并仍不是本地静态目录具备的能力；若该项是硬性要求，当前约束下尚无完整实现，须继续讨论，不能以手动更新提示代替。
